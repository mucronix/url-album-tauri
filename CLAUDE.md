## Что это за проект

**URL Album 2** — portable desktop bookmark manager на Tauri 2 + Rust + Vanilla JS.  
Духовный наследник старого URL-Album (Win32, ~2008). Хранит закладки локально в SQLite,  
без облака, без синхронизации. Философия: portable, minimalistic, classic Win32 UX.

Оригинальный URL-Album (`urlalbum.exe`, `ua.dat.bak`) лежит в корне проекта для сравнения.

## Как запустить

**⚠️ Важно**: Tauri встраивает `ui/` в бинарник при компиляции.  
**Любые изменения в JS/CSS/HTML требуют `cargo build`** перед запуском.  
Простой перезапуск exe без rebuild = старый встроенный frontend.

```powershell
# Рабочая директория: C:\Projects\url-album-tauri\src-tauri

# ⚠️ Сначала убить процесс — иначе cargo не может заменить exe (access denied)
Stop-Process -Name "url-album" -Force -ErrorAction SilentlyContinue

# Собрать и запустить (debug):
cargo build
Start-Process ".\target\debug\url-album.exe" -WorkingDirectory ".\target\debug"

# Release сборка:
cargo build --release

# Тесты слоя БД (пять штук, из той же папки src-tauri):
cargo test

# ❌ НЕ использовать cargo tauri dev — бинарник требует запущенного dev-сервера
```

**Тесты** (`#[cfg(test)] mod tests` в конце `db.rs`, появились в 2.3.2): всё на
`Connection::open_in_memory()` — ваших баз и файлов не трогают, идут за доли секунды.
Что сторожат, чтобы через полгода было понятно, можно ли их трогать:
- **порядок при импорте из другой базы** — ручной порядок источника, попадание импортированного
  в конец (а не вклиниванием между существующими), правило «папки выше ссылок», нумерация корня;
  отдельный тест прогоняет импорт десять раз и сверяет, что порядок папок одинаков — он ловит
  **недетерминированность `HashSet`**, симптом которой «каждый раз по-разному»;
- **перенос `favicon`** при импорте, вместе с проверкой соседних полей и пустого значения;
- **сдвиг индексов колонок** в `get_subtree`: заметка обязана остаться заметкой, а не получить
  имя файла снимка.

⚠️ **Новый тест обязательно прогонять на коде ДО правки и убеждаться, что он красный.** Тест,
зелёный и на сломанном коде, не проверяет ничего — за одну сессию это оправдалось дважды. Приём:
временно откатить правку скриптом по точкам, прогнать, восстановить файл из копии.

Portable-файлы рядом с exe (в `target\debug\`):
- `album.db` — база по умолчанию
- `last_db.txt` — последняя открытая база (авто-resume при старте)
- `settings.json` — настройки приложения
- `toolbar.json` — конфиг тулбара
- `browsers.json` — список браузеров
- `Data\` — скриншоты/thumbnails + `Data\favicons\` — кэш favicon файлов

### Трей и глобальный хоткей
- Иконка трея вшита: `Image::from_bytes(include_bytes!("../icons/icon.ico"))` — не полагаемся на `default_window_icon`
- **`TrayIcon` обязан пережить `setup`** — держим в `app.manage(tray)`, иначе `Drop` убирает иконку через секунду после старта
- Меню трея (`MenuItem::with_id` + `on_menu_event`): «Показать URL-Album» (`show`) / «Добавить из буфера» (`add_clip`) / «Выход» (`quit`)
- «Выход» = `app.exit(0)` → приводит к `RunEvent::Exit`, где выполняется WAL-checkpoint (см. Критические ловушки)
- Глобальный хоткей **F8** — плагин `tauri-plugin-global-shortcut`; реагировать **только на `ShortcutState::Pressed`**, иначе срабатывает дважды (нажатие + отпускание). Доп. пользовательский хоткей — `AppState.user_hotkey` / команда `set_hotkey`
- `add_from_clipboard(app)` — общая функция для трея и F8: `show/unminimize/set_focus` окна + `app.emit("tray-add-from-clipboard", ())`. Буфер читает **JS** (`navigator.clipboard.readText()` с задержкой 150мс), payload не передаётся. Если буфер начнёт приходить пустым — читать в Rust через `arboard` и слать готовый текст payload'ом
- `hide_window()` — команда «спрятать окно в трей». UI: кнопка у правого края menubar (`.menu-tray-btn`, прижата `margin-left: auto`) + пункт «Файл → Свернуть в трей» + команда `tray-hide` в `CMD_REGISTRY` (можно вынести на тулбар — актуально для компактного режима, где `#menubar` скрыт целиком)
- Возврат из трея: «Показать URL-Album» или F8 — оба зовут `show()/unminimize()/set_focus()`

### Единственный экземпляр
- Плагин `tauri-plugin-single-instance` подключён **ПЕРВЫМ** в `Builder`, до `global-shortcut`. Порядок несущий: setup-хук плагина выполняется раньше остальных и завершает вторую копию до того, как та откроет ту же базу, займёт `SERVER_PORT` HTTP-сервера расширения или перерегистрирует `urlalbum://`. Ниже по списку он сработал бы уже после чужих хуков — то есть с половиной последствий
- Версия: `"2"` в `Cargo.toml`, резолвится в **2.4.3** (требует `tauri ^2.10`, у нас 2.11.1)
- Вторая копия уходит **молча**, без единого окна: человек нажал ярлык, ему нужна программа, а не сообщение о том, что она уже запущена. Первая копия показывает окно — `show()` + `unminimize()` + `set_focus()` (то же трио, что у трея и F8; `show()` обязателен — окно могло быть спрятано в трей)
- **Ссылка `urlalbum://` из аргументов второй копии не теряется**: разбирается тем же `parse_url_scheme` и уходит в открытое окно событием `extension-add-request` — тем же, которым пользуется расширение в режиме «диалог» (payload `url` / `title` / `folder_id`), поэтому JS править не пришлось. Холодный старт по-прежнему идёт своим путём: `std::env::args()` → `AppState.pending_open` → команда `get_pending_url` при инициализации JS
- Факт второго запуска пишется в журнал вместе с аргументами — «у меня не открывается» нередко означает именно свёрнутую в трей первую копию
- Узкое место: событие уйдёт в пустоту, если вторая копия стартует в те доли секунды, пока webview первой ещё не загрузил `app.js`. Через `pending_open` не закрывали — в момент вызова колбэка `AppState` может быть ещё не смонтировано, а невостребованная запись всплыла бы при перезагрузке страницы

### Открытие ссылок
- **`resolveOpenerForNode` применяется во ВСЕХ точках открытия закладки**: двойной клик в дереве и в гриде, карточка (кнопка, адрес, двойной клик по картинке), инфо-панель, результат поиска, контекстное меню ссылки, Enter, команда `open-link`, диалог дубликатов. Резолвер поднимается до корневой папки (`findRootFolder`, `parent == null`) и берёт её `opener`, иначе — «браузер по умолчанию» из `browsers.json`. Раньше настройку учитывала только часть путей, и два способа открыть одну ссылку давали разные браузеры
- Единственная точка выхода в Rust — `openWithBrowser(url, path)`; `path || "default"` разбирается в `open_url_with`. Явный браузер (диалог «Открыть с помощью», подменю контекстного меню) резолвер намеренно обходит — там человек выбрал руками
- `open_url` — **`ShellExecuteW`**, не `rundll32` (см. Критические ловушки); `async` + `spawn_blocking`, потому что вызов возвращает управление только после разбора цели оболочкой
- `open_url_with` — **проверка пути к браузеру `Path::exists` ДО запуска**: портативный браузер мог уехать вместе с флешкой, и системный текст от `spawn` этого не объясняет. В `browser` приходит либо `"default"`, либо настоящий путь к exe (префикса `custom:` в коде нет, что бы ни говорили старые описания)
- **Отказы пишутся в журнал один раз, в Rust** — и в `open_url`, и в `open_url_with`, с причиной. JS только показывает окно через `showNotice`; дублировать `logUi` не надо
- Успехи не логируются — иначе журнал раздувается на каждой ссылке (то же правило, что у `check_url`)

### Прокси
- **Область действия — `fetch_favicon`, `check_url` и `do_screenshot`.** Скриншоты идут через прокси, **если он без авторизации** (см. Критические ловушки). Настройки читаются в Rust, поэтому прокси получают все три пути к скриншотам — одиночное «Обновить рисунок», пакет по папке и fire-and-forget из HTTP-сервера расширения, который зовёт `do_screenshot` мимо JS. Открытие ссылок в браузере — по-прежнему мимо прокси.
- `proxy_cfg_from_settings() -> Option<ProxyCfg>` — **общая точка чтения** `settings.json` для обоих потребителей (reqwest-клиент и командная строка браузера); иначе разбор camelCase-ключей и порта «числом или строкой» пришлось бы держать в двух копиях. Читает файл **при каждом вызове** — плата за то, что прокси подхватывается сразу после «Сохранить», без перезапуска
- `struct ProxyCfg { host, port: u16, user, pass }` — разобранные настройки
- `proxy_from_settings() -> Option<reqwest::Proxy>` — обёртка для reqwest
- `proxy_server_arg() -> Option<String>` — что подставить в `--proxy-server`: для прокси без логина адрес самого прокси, для прокси с логином — адрес локального релея (`relay::ensure_relay`). `None` — прокси выключен, настроен криво или релей не поднялся: скриншот делается напрямую
- **`relay.rs` — локальный релей для прокси с авторизацией.** `ensure_relay() -> Option<u16>` поднимает слушателя при первом вызове и кэширует результат в `OnceLock` (включая неудачу). Бинд на `127.0.0.1:0` — свободный порт выдаёт ОС, никаких констант: жёсткий порт означал бы тихий отказ при занятости, как у `SERVER_PORT` расширения. Слушатель в отдельном именованном потоке, на каждое соединение — свой поток (браузер открывает их пачкой)
- Релей читает настройки прокси **на каждое соединение**, а не при старте — смена прокси в диалоге подхватывается со следующего соединения, без перезапуска программы
- Две ветки обработки: `CONNECT host:port` — туннель для https (свой `CONNECT` внешнему прокси с `Proxy-Authorization`, ожидание 2xx, ответ браузеру `200 Connection Established`, дальше двунаправленное копирование в два потока); обычный запрос с абсолютным URL — голова пересылается с подстановкой своего `Proxy-Authorization`, чужой вырезается
- `relay::base64_encode` — своими руками, без зависимостей; нужен только для `user:pass` в `Proxy-Authorization`
- `strip_proxy_scheme(host)` — срезает `http://`/`https://` и хвостовой слэш; общая для `build_proxy` и `proxy_server_arg`, чтобы адрес разбирался одинаково в обоих путях
- `build_proxy(host, port, user, pass)` — общая точка сборки `reqwest::Proxy` для настроек и для проверки. Формат URL и правило basic-auth обязаны совпадать в обоих путях, иначе «Проверить» покажет успех для конфигурации, которой нет в бою
- `http_client(timeout, ua)` — единый конструктор клиента; без прокси собирает ровно прежний `Client::builder().timeout().user_agent()`
- `test_proxy(host, port, user, pass)` — проверка по параметрам **из полей диалога**, не из файла: пользователь проверяет то, что ввёл, до сохранения. Пробный запрос на `PROXY_TEST_URL` (тот же хост, что в фолбэке favicon), таймаут 8с
- Только HTTP-прокси, `Proxy::all` (весь трафик, HTTPS через CONNECT). SOCKS не поддержан, фича `socks` в reqwest не подключена
- UI: вкладка «Прокси» в настройках, кнопка «Проверить» со статусом; поля при снятой галке — `readonly`, не `disabled` (см. Критические ловушки)

### Журнал (диагностика)
- `logger.rs` — `url-album.log` рядом с exe, дозапись (`OpenOptions::append`). **Выключен по умолчанию**, ключ `logEnabled` в `settings.json`
- Флаг кэшируется в `static ENABLED: AtomicBool` — читать файл на каждую запись нельзя, при пакете скриншотов это сотни лишних чтений. `set_enabled` зовётся из JS командой `set_log_enabled` при сохранении настроек, поэтому галочка действует **без перезапуска**; при старте флаг читается один раз (`init_from_settings`)
- Размер файла кэшируется в `static SIZE: AtomicU64`: `metadata()` один раз за запуск, дальше просто прибавляется длина строки. Ротация при 2 МБ — файл переезжает в `url-album.log.old`, прежний `.old` затирается
- Запись под `static LOCK: Mutex<()>` — пишут релей (поток на каждое соединение) и `spawn_blocking` скриншотов, строки нельзя чередовать
- Время **местное**, через `GetLocalTime` из kernel32 (`extern "system"`, новых зависимостей не нужно): в std локального времени нет вовсе. UTC не годится — расходится не только час, но и дата, записи выглядят «вчерашними»
- **Пароль прокси и заголовок `Proxy-Authorization` не пишутся НИКОГДА.** В релее в журнал идут только метод и цель; голова запроса целиком — никогда, в ней этот заголовок
- **Версия WebView2 в шапке** — `tauri::webview_version()` (реэкспорт `tauri_runtime_wry` → `wry`, внутри `GetAvailableCoreWebView2BrowserVersionString`), строкой после прокси, до открытия базы. Пишется **всегда**, в том числе `WebView2: не определён (причина)`: пропуск строки при отказе неотличим от старой сборки, где записи ещё не было, а отказ здесь — самый ценный случай, окно рисует именно WebView2. Имя функции — `webview_version`, не `webview2_version`
- Что логируется: старт (версия, путь к exe, конфигурация прокси — адрес и порт, без логина, версия WebView2), открытие базы, HTTP-сервер расширения, релей (соединение, отказ подключения, не-2xx на CONNECT), `do_screenshot` — только отказ, стратегия favicon, `check_url` — обрывы связи, таймауты и ответы 4xx/5xx, отказы WAL-checkpoint и записи `last_db.txt`/`recent_dbs.txt`
- **Успехи не пишутся нигде**: ни проверка ссылки, ни снимок. Пакет на сотни ссылок иначе раздувает файл, а нужен именно перечень неудач. Сводка «получилось N из M» есть отдельно
- **Отказ снимка — одна строка**, параметры запуска внутри неё (браузер, размер, ожидание, флаг прокси). Строки перед запуском нет: у ожидания жёсткий предел `t+8`, поэтому зависший снимок всё равно доходит до записи об отказе
- **Отказ самого вызова `invoke('check_url')` пишет JS через `logUi`**: команда до своих записей не дошла, Rust о таком случае не знает. Правило «одна запись на событие» не нарушено — пишет та сторона, которая узнала первой
- UI: галочка «Вести журнал» и кнопка «Открыть журнал» в настройках, вкладка «Общие», группа «Диагностика»
- **Хук паники** ставится в `main()` до `Builder`: пишет сообщение и место (`файл:строка`), затем зовёт прежний хук. Работает и при `panic = "abort"` — хук вызывается ДО аборта и записать успевает. Флаг журнала читается там же, первой строкой `main()`, иначе паника до `setup()` не попала бы в файл
- `log_from_ui(message)` + обёртка `logUi(message)` в JS — журналирование со стороны интерфейса: `console.error` в release недоступен, DevTools отключены, и причины отказов терялись целиком
- **Сводки пакетов**: после пакета скриншотов и favicon — одна строка с итогом (всего / удалось / не удалось / секунды). Для «у меня половина картинок не грузится» это полезнее сотни отдельных записей
- Дополнительно логируются: импорт из браузеров (сколько профилей найдено, из какого файла читаем, итог; отдельная строка на «разобрано 0» с причиной), все отказы HTTP-сервера расширения (403/401/400/404/500), отказы экспорта, отсутствие Edge/Chrome для скриншота, отказы старта (открытие базы, регистрация хоткеев), откаты транзакций

    parent   INTEGER,

### Формат ua.dat (оригинал, для `importer.rs`)

## Критические ловушки

Неочевидные root causes и решения — не теряй при рефакторинге.

### Tauri / WebView2

- **WebView2 отсутствует даже там, где ЕСТЬ Edge, и наш журнал об этом не узнает.** В Windows Sandbox Edge установлен, а рантайма WebView2 нет (проверено 2026-08-06): это два разных продукта с раздельными установщиками, и Microsoft разделила их намеренно — приложению запрещено использовать браузер как движок, потому что Edge может отсутствовать или быть заморожен администратором. Отсюда следствие для нас: **наша проверка Edge для скриншотов и наличие WebView2 — независимые вещи**, найденный Edge ничего не говорит о рантайме, и наоборот. Без рантайма программа показывает английское окно от `wry` «Could not find the WebView2 Runtime» и завершается — до записи шапки журнала управление не доходит, поэтому ветка «`WebView2: не определён (причина)`» так и остаётся непроверенной: случай, ради которого она писалась, до неё не добирается. Microsoft прямо рекомендует приложению самому проверять наличие рантайма перед созданием webview. Отсюда же: формулировка «WebView2 встроен в Windows 10/11» неточна — на свежих Windows 10/11 он обычно есть, но это не гарантия. См. очередь: своя проверка до создания окна.

- **`dragDropEnabled: false` в `tauri.conf.json` обязателен.** Tauri по умолчанию перехватывает все OS-level drag-события для своего механизма drop файлов в окно — это блокирует `dragstart` на всех HTML-элементах, DnD не работает вообще.

- **`window.close()` в WebView2 уводит на `about:blank`**, оставляя пустую рамку. Закрытие только через ×/Alt+F4. Пункт "Файл → Выход" удалён по этой причине.

- **`#tree-root-drop` обязан быть вне потока.** Показ/скрытие через `display: block` во время `dragstart` вызывает sidebar reflow → сдвигает drag-source → Chromium/WebView2 немедленно отменяет drag (firing `dragend`). Текущее решение: `opacity: 0/1` + `pointer-events: none/auto` — DOM не меняется, reflow нет.

- **`eprintln!`/`dbg!` не видны в GUI-сборке** (`windows_subsystem = "windows"`). DevTools в release отключены. Для отладки: `"devtools": true` в `tauri.conf.json` временно, или журнал (`logger::log`, см. раздел «Журнал»).

- **Отказ `setup` приходит ПАНИКОЙ, а не тихим выходом.** Возврат `Err` из `setup` Tauri превращает в панику внутри себя (`tauri/src/app.rs`, «Failed to setup app: error encountered during setup hook»). Именно это и есть «окно просто не появилось» при повреждённой базе. Без хука паники в журнале не остаётся ничего — проверено на битом `album.db` (сессия 20, `32cd6fe`): в файле оказались обе строки, наша причина и сама паника.

- **Регистрация глобального хоткея не должна ронять запуск.** Раньше `on_shortcut("F8")` в `setup` шёл через `?`, и занятая чужой программой комбинация означала, что окна не будет вовсе. Теперь отказ пишется в журнал, запуск продолжается. То же правило для любых внешних ресурсов в `setup`: они не критичны для показа окна.

- **`#[tauri::command]` не позволяет пометить команду `pub(crate)`.** Макрос генерирует `__cmd__<имя>` и `__tauri_command_name_<имя>`, и при добавлении видимости они конфликтуют сами с собой — `error[E0255]: the name __cmd__<имя> is defined multiple times`. Если тело нужно другому модулю, выносить его в обычную функцию, а команду оставлять тонкой обёрткой. Так сделано с `read_settings_raw` / `load_settings`.

- **WAL-checkpoint при выходе возможен только в `RunEvent::Exit`.** Managed-состояние (`app.manage`) при завершении Tauri **не дропается** — `Connection::drop` → `sqlite3_close` не вызывается, WAL не вливается в базу. Форма `.run(tauri::generate_context!())` без колбэка `RunEvent` не видит вообще. Решение: `.build(ctx)?.run(|app_handle, event| …)`, внутри `if let RunEvent::Exit` → `app_handle.try_state::<AppState>()` → `PRAGMA wal_checkpoint(TRUNCATE)`, ошибки игнорировать (выход не блокировать). `app.exit(0)` из трея приходит сюда же — отдельный checkpoint в обработчике трея не нужен. **Файлы `-wal`/`-shm` при этом остаются на диске — это норма**: соединение не закрывается, checkpoint лишь переливает данные в основной файл. (Сессия 20, `36defd3`.)

- **Обработчики `contextmenu` в JS точечные — дыры неизбежны.** Они висят на конкретных элементах (дерево, грид, detail-view, строки диалогов), а в непокрытых местах — пустота под деревом, отступы, тулбар, breadcrumb, `gridEl` мимо `.card` — всплывает родное меню WebView2 («Назад / Обновить / Сохранить как / Печать»), иногда поверх нашего. Решение: один глобальный перехватчик на `document` в **фазе всплытия** (без `capture`) в конце `init()` — точечные обработчики отрабатывают первыми, `e.preventDefault()` гасит остаток. `INPUT`/`TEXTAREA`/`isContentEditable` исключены, иначе пропадёт «Вырезать/Копировать/Вставить». (Сессия 20, `bbb43b1`.)

### Rust — IPC и блокировки

- **Блокирующие команды (`std::process::Command::status()` и т.п.) — обязательно `async fn` + `spawn_blocking`.** Иначе IPC-поток замерзает и UI не реагирует. Касается: `refresh_thumb`, любой команды, запускающей внешний процесс.

- **Не держать `MutexGuard` через `.await`.** В async-командах: взять `db.lock()`, выполнить запрос, отпустить guard до первого `.await`.

- **Tauri 2: направление конвертации имён.**
  - JS → Rust (аргументы `invoke`): camelCase **конвертируется** в snake_case автоматически. `invoke('cmd', { sortIdx: 5 })` доходит до параметра `sort_idx: i64`; аналогично `parentId → parent_id`, `newPath → new_path`.
  - Rust → JS (поля ответа, сериализованные структуры): **НЕ конвертируются**, остаются snake_case. Структура с полем `sort_idx` приходит в JS как `n.sort_idx`, не `n.sortIdx`. При обращении к полям ответа всегда использовать snake_case.

### Rust — строки и кодировки

- **`u8 as char` в Rust — это Latin-1, а не UTF-8**: код символа равен значению байта. Раскодировать процентные последовательности, накапливая результат в `String` через `push(b as char)`, нельзя: одна буква кириллицы приезжает двумя парами (`%D0%9F`), каждый байт становится отдельным символом `U+00D0`/`U+009F`, и `String` кодирует их обратно в UTF-8 уже двумя байтами каждый. Двойная перекодировка: «Проверка» → «ÐŸÑ€Ð¾Ð²ÐµÑ€ÐºÐ°». **ASCII при этом цел** — на латинице баг незаметен, поэтому в `urlalbum://add?url=…&title=…` адрес выглядел исправным, а название нет. Копить `Vec<u8>`, собирать `String::from_utf8_lossy`. Заодно: `u8::from_str_radix` принимает знак (`from_str_radix("+f", 16)` = `Ok(15)`) — для разбора hex-пар надёжнее своя таблица на четыре ветки, иначе корректность держится на том, что `+` заменён строкой выше. (Сессия 21, `3cd9b95`.)

### SQLite / rusqlite

- **`WHERE parent IS ?1` вместо `= ?1` при работе с NULL.** SQLite: `NULL = NULL` → false; `NULL IS NULL` → true. Используется в `move_node` и фильтрации корневых узлов.

- **`sort_idx` обязан быть в SELECT и в `struct TreeNode`.** Без поля `pub sort_idx: i64` в `TreeNode` фронтенд получает `undefined` — все `.sort((a,b) => (a.sort_idx??0)-...)` тихо сводятся к сортировке по `id`. Симптом: порядок сбрасывается при каждом перезапуске, хотя в БД записано верно. Дерево "работало" случайно — V8 стабильная сортировка сохраняла порядок из `ORDER BY sort_idx,id`.

- **И `thumb`, и `favicon` хранят только filename**, путь собирается в runtime: `exe_dir/Data/{thumb}` и `exe_dir/Data/favicons/{favicon}`. Старые базы с абсолютными путями в `thumb` чинит `migrate_thumb_to_filename` при открытии базы — она же вызывается в `switch_db`. Раньше `thumb` хранил абсолютный путь, и при переносе папки скриншоты ломались; сейчас нет.

- **`execute_batch` НЕ атомарен.** Операторы выполняются подряд, каждый фиксируется сам по себе, и отказ на середине оставляет уже выполненное в базе. Так `clear_db` удалял `nodes` и падал на `DELETE FROM entries` — таблице старой схемы, которой `db::init` не создаёт: данные стёрты, команда вернула ошибку, `VACUUM` не выполнился, человек считал, что очистка не сработала. Проверено на копии базы: **0 узлов из 782 при возвращённой ошибке**. Многошаговые операции оборачивать в `BEGIN`/`COMMIT`/`ROLLBACK` вручную — так сделано в `delete_folder` и `clear_db` (сессия 20, `0f7cb5d`, `a52a7e7`).

- **`VACUUM` не работает внутри транзакции — только после `COMMIT`.** И его отказ не должен превращаться в ошибку команды, если данные уже зафиксированы: иначе снова получим «не сработало» при том, что сработало. `PRAGMA journal_mode = WAL` после `VACUUM` восстанавливать **отдельным батчем** — в одном с `VACUUM` она падает вместе с ним, и база остаётся без WAL.

- **`backup_db` / `backup_db_with_data` копируют только `*.db`, без сайдкара `*.db-wal`** — всё, что лежит в WAL, в копию не попадёт. Перед `std::fs::copy` обязателен `PRAGMA wal_checkpoint(TRUNCATE)`, и делать его **после** `save_file().await` / `pick_folder().await` (диалог асинхронный). **`MutexGuard` через `.await` не держать** — checkpoint вынесен в синхронную `checkpoint_before_copy()`, где guard берётся и отпускается целиком внутри тела, так что нарушить правило структурно невозможно. Неудачный checkpoint не отменяет копирование (файл валиден, просто без свежих записей) — предупреждение уходит наверх текстом через `backup_result()`. (Сессия 20, `36defd3`.)

### Скриншоты (thumbnails)

- **`MAX_THUMB_CONCURRENCY = 1` — не поднимать.** При > 1 воркеры стартуют в одну секунду → одинаковый timestamp → один файл → браузеры перезаписывают друг друга → скриншоты путаются между ссылками. Имена теперь детерминированные `{id}.png` (перезапись без дублей), но ограничение `=1` остаётся.

- **Уникальный `--user-data-dir` per invocation** (`ua_screenshot_{id}`) — иначе конфликт профилей Edge/Chrome headless при параллельных вызовах.

- **Готовность скриншота = ПОЯВЛЕНИЕ ФАЙЛА, а не выход процесса браузера.** Headless Edge/Chrome-родитель может выйти ДО записи PNG дочерним процессом (на быстрых машинах — выход за ~260мс с файлом 0 КБ); плюс Windows Defender задерживает видимость только что созданного файла на **незнакомых путях** (репутационный скан новой/переименованной папки). Поэтому `do_screenshot` решает по `path.exists()` (записанный файл = успех, даже если браузер убит/вышел не чисто) + **ретрай ожидания файла с потолком = `t` секунд** (настройка «Время ожидания», НЕ зашитое число), плюс поллинг стабильного размера и дедлайн `t+8`. Имя **детерминированное `{id}.png`** (`remove_file` перед spawn → без дублей; cache-busting `?v=` в UI; авто-обновление detail-view в `_applyThumbToCard`). Симптом до фикса: на быстром ПК сохранялось 14/46, на медленном ноуте — всё ОК. Дефолт ожидания 12с. (Сессия 19, `a2309df`.)

### Прокси

- **Rust впервые парсит `settings.json`.** Раньше `load_settings` отдавал сырую строку в JS, и Rust о содержимом не знал. Теперь `proxy_from_settings` разбирает его в `serde_json::Value`. Ключи — **camelCase**, как их пишет JS (`proxyEnabled`, `proxyHost`, `proxyPort`, `proxyUser`, `proxyPass`); автоконвертации имён тут нет — это файл, а не IPC. Порт принимается **и числом, и строкой**: `<input type="number">` может записать любой из двух вариантов. Любая проблема разбора → `None` → сеть идёт напрямую, а не падает.

- **Отказ авторизации на CONNECT-туннеле приходит СЛОВАМИ, без кода.** Реальная цепочка: «error sending request for url (...); client error (Connect); tunnel error: **proxy authorization required**», флаги `connect=true`, `status=None`. Подстроки «407» в тексте нет, `r.status()` недоступен — при https запрос не доходит до HTTP-уровня. Отсюда `is_proxy_auth_error()` ищет в нижнем регистре три подстроки: `proxy authorization required`, `proxy authentication required`, `407` (последняя — на случай http-запроса без туннеля). (Сессия 20, `66c7691`.)

- **Порядок веток `match` в `test_proxy`: распознавание авторизации ОБЯЗАНО стоять выше `is_connect`.** У отказа авторизации `connect=true`, поэтому нижняя ветка перехватит случай раньше, и пользователь увидит «Прокси не отвечает: проверьте адрес и порт» вместо «требует авторизацию». Ветки `match` вычисляются сверху вниз — порядок здесь несущий, а не косметический.

- **`Proxy::all`, а не `Proxy::http`.** Последний ловит только http-запросы, а favicon и проверка ссылок идут по https — трафик пошёл бы мимо прокси. Выглядело бы как «прокси не работает» при внешне верных настройках.

- **Chromium игнорирует логин и пароль в `--proxy-server`** — на 407 он показал бы диалог авторизации, которого в headless нет, и завершился бы молча, без PNG. Поэтому для прокси с логином браузеру отдаётся адрес локального релея (`relay.rs`), а тот уже подставляет `Proxy-Authorization` при походе на внешний прокси. Передавать учётные данные в самом флаге бессмысленно в любом виде.

- **Голова HTTP в релее читается ПОБАЙТНО, не через `BufReader`.** Буферизованное чтение утащило бы в свой буфер байты, идущие сразу за `\r\n\r\n` — то есть начало TLS-рукопожатия, — а сырое копирование их бы не увидело: туннель ломался бы на первом же соединении. Побайтное чтение с потолком 32 КБ снимает проблему целиком.

- **`tiny_http` для CONNECT не годится, несмотря на `Request::upgrade`.** Тот принудительно печатает `Connection: upgrade` и `Upgrade: <protocol>` (он сделан для вебсокетов), а браузер на CONNECT ждёт голый `200 Connection Established`. Плюс однопоточный `incoming_requests()` не удержит несколько туннелей разом. Релей поэтому написан на `std::net::TcpListener` — новых зависимостей не потребовалось (`tokio` подключён только с фичей `time`, `tokio::net` недоступен).

- **Релей слушает 127.0.0.1 без авторизации.** Пока он поднят, любой локальный процесс может ходить через прокси пользователя, не зная логина. Смягчает только то, что порт случайный (`127.0.0.1:0`) и меняется при каждом запуске. Если понадобится закрыть — поднимать релей на время пакета скриншотов и гасить после, а не держать до конца процесса. (Сессия 20, `79762b5`.)

- **Ошибки прокси в `do_screenshot` не диагностируются вовсе.** stdout/stderr headless-браузера не читаются, отдельного канала ошибок нет, решение принимается по факту наличия PNG — отсутствие файла неотличимо от «сайт не открылся». Единственная подсказка человеку — приписка «(включён прокси — проверьте его доступность)» в тексте ошибки, и вешается она по флагу `proxy_used`, то есть **только когда флаг реально передан**. Приписки нет, когда флаг не передавался вовсе — прокси выключен, настроен криво или релей не поднялся; тогда трафик действительно шёл напрямую и упоминание прокси было бы ложным следом. (Сессия 20, `718b9ca`.)

### Журнал и настройки

- **BOM в `settings.json` молча ломал ВСЕ настройки, а не только их чтение.** `serde_json` не разбирает строку, начинающуюся с `EF BB BF`, но хуже другое: `JSON.parse` в `loadAppSettings` падает точно так же, фронтенд откатывается на значения по умолчанию и при первом же сохранении **затирает файл**. Итог: человек открыл `settings.json` блокнотом и сохранил — потерял прокси, тулбар, размеры панелей, всё. Лечится в `read_settings_raw`: `trim_start_matches('\u{feff}')`; строка без BOM уходит и в JS, поэтому чинятся обе стороны разом. (Проверено, сессия 20, `89aba56`.)

- **`load_or_init_token` — ВТОРОЙ путь чтения `settings.json`, мимо `read_settings_raw`.** Она читает файл сама и при неразобранном JSON перезаписывала его одним токеном: настройки исчезали **до старта окна**, а JS получал уже валидный файл и никакой ошибки не видел. Из-за этого починка BOM в `89aba56` этот путь не покрывала. Теперь BOM срезается и здесь, копия кладётся в `settings.json.bad`, поднимается `SETTINGS_WERE_RESET` — UI спрашивает флаг командой `settings_were_reset` и показывает уведомление. **Новые места чтения настроек заводить только через `read_settings_raw`.** Побочно: при испорченном файле журнал не включится — флаг `logEnabled` живёт в нём же. (Сессия 20, `1c518a6`.)

- **Событие пишется в журнал РОВНО ОДИН раз, и правило работает в обе стороны.** Записывает та сторона, которая первой узнала причину; вторая только показывает её человеку. Отказ открытия ссылки логируется в Rust (`open_url`, `open_url_with`), и `openWithBrowser` в JS его не повторяет — он получает готовый текст и лишь вызывает `showNotice`. Наоборот: разбор испорченного `settings.json`/`browsers.json`/`toolbar.json` происходит в JS, поэтому пишет `logUi`, а Rust в `backup_bad_config_file` фиксирует только своё действие — что копия отложена как `.bad`. Две записи на одно событие мешают дважды: при разборе жалобы кажется, что отказ случился дважды, и файл раздувается там, где он и так собирает пакетные операции.

- **`open_file` раньше НЕ возвращала ошибку на несуществующем пути** — делала `spawn` на `cmd /c start`, и сам запуск удавался всегда, а отказ происходил уже внутри `cmd`, куда нам не видно. Переведена на тот же `ShellExecuteW`, что и открытие ссылок: отсутствующий файл даёт код 2, и `Err` теперь достоверен. Проверка в `get_log_path` (возвращает `None`, если файла нет) осталась — она сообщает об этом до попытки открыть и позволяет сказать человеку, что журнал ещё не создан, а не «не удалось открыть». Все три вызова в JS обрабатывают отказ; без `catch` это молчаливый unhandled rejection.

### Импорт браузеров (Chromium профили)

- **`detect_browsers_list` сканирует ВСЕ профили в `User Data` (`read_dir`, по образцу Opera-скана), а не только `Default`.** Иначе Edge/Brave с не-Default профилем (`Profile 1`/`Profile 2` — типично при входе в аккаунт) не находятся для импорта, хотя «Обнаружить браузеры» (`detect_browser_exes`, по `.exe`) их видит. Ключ: **импорт ищет файл `Bookmarks` в профиле, обнаружение — `.exe`** → браузер может быть установлен без `Default\Bookmarks`. Каждый профиль с `Bookmarks` = отдельная запись **«Браузер — Профиль»**, id `{браузер}__{папка}` (стабилен — `import_from_browser` повторно зовёт `detect_browsers_list` и ищет по id). Формат у всех Chromium один (`import_chromium`); Firefox/Opera — свои сканы, не трогать. (Сессия 19, `499170c`.)

- **Файл `Bookmarks` создаётся не при установке браузера и не при создании профиля, а при первом изменении списка закладок.** Проверено на чистой Windows 10 (VirtualBox, 2026-08-06): свежий Edge виден в «Обнаружить браузеры» (поиск по `.exe`), но в «Импорт из браузера» его нет — импортировать нечего, файла ещё не существует. После добавления первой закладки запись появляется. **Это не баг**, а прямое следствие правила выше: обнаружение идёт по `.exe`, импорт — по `Bookmarks`, и на свежей системе два списка законно расходятся. Там же подтвердился и сам скан профилей: профиль назывался `Profile 1`, не `Default`, и обход всех подпапок `User Data` отработал верно.

### Браузерное расширение

- **`POST /api/v1/handshake`, не GET.** Браузер не шлёт заголовок `Origin` на простые GET-запросы — Origin-проверка всегда давала 403. POST шлёт Origin.

- **`GET /api/v1/folders` — Origin-проверка ослаблена намеренно.** Браузер не шлёт Origin на GET без кастомных заголовков → нельзя требовать совпадение. Защита — токен `X-UA-Token`. Логика: Origin прислан и не совпадает → 403; пустой → пропустить.

- **Extension ID `imekfalcnffmmmabcjapmihbocjabecf` зафиксирован через `"key"` в `manifest.json`.** Приватный ключ `extension-keys/private.key.pem` **не в git** (`extension-keys*/` в `.gitignore`) — нужен для восстановления того же ID. Не потерять.

### Открытие ссылок

- **`rundll32 url.dll,FileProtocolHandler` всегда завершается нулём** — нашёлся браузер или нет. Отсюда и слепое пятно: человек кликал ссылку, ничего не происходило, программа возвращала `Ok`, в журнале пусто. `ShellExecuteW` возвращает HINSTANCE: **больше 32 — успех, иначе само число и есть причина отказа** (2 — не найдена программа-обработчик, 3 — не найден путь, 5 — доступ запрещён, 26 — файл занят, 31 — нет программы для ссылок этого вида).

- **Незнакомая схема отказом НЕ считается.** Windows 10/11 перехватывает её своим окном «Вам понадобится новое приложение» и возвращает **успех**: проверено вызовом, `zzznotascheme://x` дал код 42. Отказы приходят на файловый класс причин — несуществующий путь дал 2. Значит «в системе не назначен браузер» этим способом не диагностируется, и обещать такое в интерфейсе нельзя.

- **Отказ логируется ОДИН раз, в Rust** (`open_url`, `open_url_with`). В JS не дублировать: `openWithBrowser` получает уже записанную причину и только показывает окно. Частный случай общего правила «одно событие — одна запись», см. «Журнал и настройки»: здесь причину первой узнаёт Rust, а при разборе испорченных настроек — наоборот, JS.

- Doc-комментарий (`///`) к `extern`-блоку не крепится — rustc отвечает `unused doc comment`. Пояснение к `ShellExecuteW` намеренно обычным `//`.

### Сборка и линковка

- **Rust на Windows по умолчанию линкуется с C++ runtime ДИНАМИЧЕСКИ**, и собранный exe требует `VCRUNTIME140.dll` из Microsoft Visual C++ Redistributable. На машине разработчика он есть всегда — его ставят Build Tools, — поэтому **баг незаметен ровно там, где его ищут**: у себя программа запускается, а на чистой Windows 11 24H2 не стартует вовсе, с системным окном «не обнаружена VCRUNTIME140.dll». Лечится `rustflags = ["-C", "target-feature=+crt-static"]` в `.cargo/config.toml`. Цена — **143 КБ** к размеру exe (9 140 736 → 9 287 168 байт на 2.3.0-beta), прилинковывается только используемая часть CRT. Для portable-программы, которую переносят флешкой и запускают на чужой машине, это обязательно: установщика у нас нет и просить поставить runtime некому. **Подтверждено живьём** на чистой Windows 10 в VirtualBox без Visual C++ Redistributable (2026-08-06) — программа запускается. До этого проверка была только по таблице импортов, то есть косвенная: она показывает, что зависимости в файле нет, но не то, что программа стартует.
  - **Проверка:** строка `VCRUNTIME140.dll` не должна встречаться в exe (имена импортируемых DLL лежат в PE обычным текстом).
    - **Контроль метода — положительный, по тому же файлу:** `KERNEL32.dll` обязана найтись в любой сборке. Не нашлась — значит сломан поиск, а не линковка, и отрицательный результат по `VCRUNTIME140.dll` ничего не доказывает.
    - **Debug эталоном «сборки без флага» БОЛЬШЕ НЕ ЯВЛЯЕТСЯ.** `.cargo/config.toml` лежит в `src-tauri/` и применяется ко **всем профилям**, собираемым оттуда, поэтому debug с `cf102d1` тоже линкуется статически. Прежняя запись «в debug-сборке без флага она есть» устарела в день написания — на ней уже спотыкались при выпуске 2.3.1-beta.
    - По `USER32.dll` и `ADVAPI32.dll` **не проверять**: в импортах их может не быть вовсе, символы приходят через другие библиотеки. Годятся только те имена, что заведомо присутствуют.

- **Найденная в exe строка НЕ доказывает, что код её пишет.** Метод выше годится для имён импортируемых DLL, но для собственных сообщений он врёт: в бинарник попадают строки **зависимостей**. Проверено сегодня — искали, почему в журнале нет версии WebView2, нашли в exe `WebView2: ` и решили, что вызов есть, а он «не срабатывает». На деле найденное принадлежало загрузчику из `wry`/`webview2-com` (`WebView2: Failed to find the app exe path.`, `WebView2: Failed to find an installed WebView2 runtime` и ещё три), а нашего вызова не существовало вовсе — совпал формат «слово, двоеточие, пробел». Строки попадают в бинарник и другими путями: `include_bytes!`/`include_str!` вшивают содержимое файла целиком (у нас так вшита иконка трея). **Доказательство — вызов в исходниках**: `grep` по имени функции плюс `git log -S` (появлялась ли строка хоть в одной ревизии). Поиск по exe оставить для того, для чего он верен, — таблицы импортов.
  - **Оговорка о расположении:** конфиг лежит в `src-tauri/.cargo/`, а cargo ищет его от текущего каталога вверх. При сборке из `src-tauri` (как описано в «Как запустить») он подхватывается; при запуске cargo из корня репозитория через `--manifest-path` — **нет**, и exe тихо соберётся с динамическим CRT.
  - Секция задана условием `[target.'cfg(target_env = "msvc")']`, а не жёсткой тройкой `x86_64-pc-windows-msvc`: покроет и ARM64, если понадобится.
  - (Жалоба с форума, сессия 21, `cf102d1`.)

Тот же прогон переписывает файлу переводы строк: `app.js` дал 545 изменённых строк вместо одной. При подготовке 2.3.1-beta так испортились разом `Cargo.toml`, `tauri.conf.json`, `extension/manifest.json` и `app.js`; поймано в рабочем дереве до `git add`, поэтому **в истории репозитория следов нет** — искать их там бесполезно. Правильно: точечная замена строки (`Edit`) либо `[IO.File]::WriteAllText` с `UTF8Encoding($false)`. Для JSON цена ошибки высокая — BOM ломает разбор молча, см. «Журнал и настройки».

Работает потому, что ни один релиз не помечен pre-release'ом (`prerelease: false` у всех) — `latest` их видит. Если когда-нибудь выложить настоящий pre-release, `latest` его пропустит и покажет предыдущий; тогда либо не ставить флаг, либо вернуться к прямой ссылке на тег.

### Поддерживаемые ОС

- **Минимум Windows 10.** WebView2 требует `ProcessPrng` из `bcryptprimitives.dll` — появилась в Windows 8+. На Win7 WebView2 (включая v109) падает с "ProcessPrng не найдена". DLL-шим отклонён — антивирусы флагают как малварь.

### JS — синхронизация дерева и грида

- **После изменения порядка/содержимого обновлять ОБА — дерево (`renderTree`) И грид (`loadFolderContents`/`loadBookmarks`) + синхронизировать `allNodes sort_idx`.** Рендерятся раздельно, легко забыть одно. Баг повторялся трижды: favicon batch не обновлял дерево (п.59), drag-сортировка папок не обновляла грид, `sort_folder` не обновлял грид (allNodes был stale). Паттерн: `allNodes[i].sort_idx = newIdx` → `renderTree` → `loadFolderContents`/`loadBookmarks`.
- **`dataDir` обновлять в `showApp` при каждом открытии базы, не только при старте.** Задаётся один раз в `init` → при `switch_db`/`open_db` остаётся от первой базы → картинки и favicon второй базы ищутся в `Data/` первой. Фикс: `dataDir = await invoke('get_data_dir')` в начале `showApp` перед `renderTree`.

### Работа с git

- **Не редактировать рабочий код ради разделения коммитов.** Дважды за две сессии возникал соблазн разложить одну правку на два коммита: то нарезать патч по ханкам, то временно вернуть в файл старую версию функции, закоммитить первую часть и вписать новую обратно. Второй раз это оборвалось на середине обрывом связи, и пришлось отдельно проверять, что вообще осталось в файле. Красивый лог не стоит риска потерять правку: если куски в одном файле не делятся штатными средствами — **объединять в один коммит** и говорить об этом вслух. (Сессия 21.)

## Паттерны и соглашения

### Ссылки в документации
- **Номера строк не писать.** Они устаревают при каждом коммите, и проверить их дороже, чем найти заново: ссылаться на **имя функции, константы или запроса** — `grep` найдёт всегда. Так уже дважды получалось разночтение: `backup_db (1270)` и `INBOX_FOLDER_NAME (main.rs:24)` разъехались за одну сессию. То же про счётчики вида «во всех 15 вызовах» — считать `grep -c`. В сообщениях коммитов и в разборе номера уместны: там они привязаны к конкретной ревизии.

### Rust
- Все команды через `state: tauri::State<AppState>`
- `move_node`, `create_bookmark` и т.д. — параметры в snake_case (Tauri конвертирует из camelCase)
- `CREATE_NO_WINDOW (0x0800_0000)` на все `Command::new` для консольных exe
- `normalize_url()` — вызывается в open_url, open_url_with, refresh_thumb, fetch_favicon, check_url
- `open_url` использует **`ShellExecuteW`** — не `rundll32 url.dll,FileProtocolHandler` (всегда возвращал ноль, отказы были невидимы) и не `cmd /c start` (ненадёжно). Заменено в `407fb21`, подробности в «Критических ловушках»
- Async команды (fetch_favicon, check_url, refresh_thumb): НЕ держать MutexGuard через `.await`
- Команды с блокирующими процессами (`std::process::Command::status()`) — обязательно `async fn` + `tauri::async_runtime::spawn_blocking`, иначе IPC-поток замерзает и UI не реагирует
- `favicon` в DB: только filename (`github.com.png`), путь = `exe_dir/Data/favicons/{filename}`

### JS
- `allNodes` — in-memory кэш всего дерева, обновляется через `invoke('get_tree')`
- `allFolders` — производная от `allNodes`
- `activeFolderId` — текущая папка в grid
- `activeBookmarkNode` — выделенная ссылка (null в list mode)
- `dataDir` — путь к Data/ (без trailing slash, загружается в init())

- `_dragNode` — глобальное состояние DnD

- `raiseOverlay(el)` — перемещает overlay в конец body для правильного z-index
- `convertFileSrc(path)` — Tauri asset:// URL для локальных файлов

### Принятые решения (почему так)

Перенесено из `DECISIONS.md` — только то, что не выводится из здравого смысла и до сих пор верно.

- **`asset://` для PNG, не base64 через IPC.** base64 означал бы копирование картинки через IPC на каждую карточку; `asset://` отдаёт файл напрямую WebView-ом. Заметно на больших папках — меньше памяти и быстрее рендер.
- **Единая таблица `nodes` с полем `kind`, а не отдельные `folders` и `bookmarks`.** Дерево строится из одной таблицы, без JOIN-ов, глубина иерархии не ограничена (adjacency list).
- **Vanilla JS без фреймворка.** Нет бандлера — нет шага сборки фронтенда, `node_modules` и версионных конфликтов; `withGlobalTauri: true` даёт `window.__TAURI__`, этого достаточно.
